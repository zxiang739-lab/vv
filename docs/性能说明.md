# FrameFlowAI 性能说明

本文档说明本工程的性能瓶颈、ANE/GPU 优化手段、内存风险与实时模式延迟控制要点。

---

## 1. 性能瓶颈

| 环节 | 瓶颈 | 本工程处理 |
|---|---|---|
| 摄像头采集 | 传感器 / ISP 帧率上限 | 720p 采集（`AVCaptureSession.Preset.hd1280x720`），可调 |
| 像素格式转换 | 非引擎所需格式时需 CVPixelBuffer 转换 | 相机/读取器统一 BGRA，CoreML 图像输入零拷贝直通；VT 会话仅在源格式不被支持时兜底转换 |
| 帧插值 | 神经引擎每帧推理耗时 | 实时用低延迟配置（专为逐帧低延迟设计）；离线用高质量配置换画质 |
| 超分辨率 | 输出分辨率越大，GPU/ANE 负载越高 | 默认 2x，避免 4x 造成实时不可用 |
| 编码器 | H.264 编码速度 | 离线异步，实时不编码 |
| 背压 | 处理跟不上采集 | 实时链路丢弃积压帧，保证端到端延迟稳定 |

> **核心规律**：实时链路的可达 FPS ≈ `1 / 单帧端到端耗时`。单帧耗时 = 采集 + 格式适配 + AI 推理 + 预览入队。
> 其中 AI 推理通常占绝对大头；低延迟 VT 配置（VTLowLatencyXXX）专门针对 < 单帧时间 的推理做了优化。

## 2. ANE / GPU 优化

- **VTFrameProcessor**：系统自动调度神经引擎（ANE），对 iPhone 的 NPU 做最佳利用，无需开发者干预；
  低延迟配置专门为「每帧毫秒级推理」设计。
- **CoreML**：`MLModel.prediction` 由 CoreML 自动选择 GPU / ANE / CPU 执行单元。优化建议：
  - 模型量化：FP16 / Int8（coremltools 转换时 `--quantization`），可显著提速、降内存；
  - 固定输入尺寸：避免每帧动态 shape 造成的重编译 / 重分配；
  - 批量推理（本工程逐帧，如需吞吐可一次给多帧）——补帧模型本身就是双帧输入，天然带批维度；
  - 复用 `MLModel` 实例（本工程在 `CoreMLInferenceStage` 持有单例模型，跨帧复用，不做每帧加载）。
- **像素操作**：缩放用 `vImageScale_ARGB8888`（Accelerate，SIMD 加速）；通道重排手写 SIMD 友好循环；
  `CIContext` 实例全局复用（`CoreMLPixelBufferUtility` / VT 会话共享实例）。
- **输出缓冲池**：VT 会话用 `CVPixelBufferPool`（MinimumBufferCount=6）帧级复用，避免每帧 `CVPixelBufferCreate` 的分配抖动。

## 3. 内存风险与防范

| 风险 | 说明 | 防范 |
|---|---|---|
| 每帧临时缓冲堆积 | 处理跟不上时中间缓冲无限累积 | 实时背压（丢弃新帧）+ 串行处理队列；离线逐帧串行 + 每帧局部作用域回收 |
| 双帧补帧模型的中间态 | 补帧需保留上一帧（VTFrameProcessorFrame / CVPixelBuffer） | 每会话仅保留 1 帧上下文（previousFrame / previousOutputFrame） |
| 离线长视频 | 音频样本收集数组随时长增长 | 音频按 23ms/样本收集，2 分钟 ≈ 5k 样本（约 20–50MB），可接受；极长视频可改为边读边写 |
| 模型加载 | MLModel 首次加载占用内存 | 仅在使用时加载（prepare 阶段），stop 时释放（`CoreMLFrameProcessingEngine.stop()` 置 nil） |
| 超高分辨率输出 | 4K 超分输出缓冲很大 | 默认 2x；离线时建议源 ≤ 1080p |

## 4. 实时模式延迟控制要点

1. **低延迟配置优先**：实时一律走 `VTLowLatencyFrameInterpolationConfiguration` /
   `VTLowLatencySuperResolutionScalerConfiguration`，它们按「每帧 < 帧间隔」目标设计；
   **绝不在实时链路用高质量配置**（其为离线高质量优化，单帧耗时可远超帧间隔）。
2. **丢弃迟到帧**：`AVCaptureVideoDataOutput.alwaysDiscardsLateVideoFrames = true`，避免采集积压。
3. **背压调度**：`RealtimePipelineService` 用布尔标志丢弃「上一帧仍在处理时」到达的新帧，
   队列深度恒为 0/1，端到端延迟 ≈ 采集延迟 + 单帧推理耗时。
4. **零拷贝优先**：相机输出 BGRA 与 CoreML 图像输入直接复用（`toBGRA` 直通）；VT 会话在源格式受支持时不转换。
5. **不阻塞 UI**：引擎 `prepare`（模型加载可能 > 1 帧时间）在后台执行；预览用 `AVSampleBufferDisplayLayer.enqueue`（线程安全）。
6. **监控反馈**：`PerformanceMonitor` 实时统计 FPS（1s 滑窗）与端到端延迟（滑动平均），
   UI 叠加显示；若 FPS 明显低于采集帧率，说明推理成为瓶颈，建议降低分辨率 / 倍率或换低延迟模型。
7. **首帧开销**：补帧 / 高质量超分需要时序上下文（前一帧），首帧透传是设计行为，不要视为异常。

## 5. 硬件占用展示的说明

- `SystemMetrics.cpuUsage()`：通过 `host_processor_info` 两次采样差值计算的是**系统全局**忙碌度（进程级需累加线程时间，工程为简化返回全局 busy，UI 已标注「系统繁忙度」）。
- 内存：`task_vm_info.resident_size`（进程常驻内存）。
- **ANE / GPU 实时占用率没有公开 API**；本工程以「CPU% + 内存 + 单帧推理耗时（lastFrameProcessingTime）」共同代理硬件负载，
  精确的 ANE/GPU 占用需用 **Instruments（Metal System Trace / Neural Engine）** 观测。

## 6. 可调参数建议

| 参数 | 位置 | 建议 |
|---|---|---|
| 摄像头预设 | `CameraService.start(preset:)` | 720p 平衡速度与画质；追求低延迟可 540p |
| 补帧倍数 | `EngineConfiguration.numberOfInterpolatedFrames` | 实时 1（30→60）；离线可按需 2–3 |
| 超分倍率 | `EngineConfiguration.superResolutionScaleFactor` | 实时 2.0；离线 2–4 视设备 |
| 目标帧率 | `EngineConfiguration.targetFrameRate` | 离线补帧时显式指定以获得整数倍率 |
| 输出码率 | `OfflinePipelineService.estimatedBitrate` | 每像素 0.1bit×fps，自动估算 |
